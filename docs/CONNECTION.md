# 连接与发现：现状、候选与取舍

记录一次关于「让手机连上电脑上的 Kite 更方便、更安全」的设计讨论。**本文只是记录，没有任何实现**；Kite 本体一行代码未动。后续要不要做、先做哪几件，等决定。

## 一、问题

1. Kite 默认只监听 `127.0.0.1`（`internal/cli/serve_cmd.go` 里的 `--addr` 默认空），手机要连必须加 `--addr 0.0.0.0:1717`——既难记，又把包括 VPN 虚拟网卡在内的所有网卡一起暴露。
2. 电脑的地址是 DHCP 租的，会变（实测从 `10.149.156.249` 变成 `172.30.56.249`），手机里存的地址跟着失效。
3. 用户侧没有路由器，做不了端口映射、也做不了路由器级 VPN；手机与电脑不在同一 `/24` 时，客户端的扫描式发现必然失败——它只扫手机自己所在的那个网段。
4. 真要走公网，Kite 目前只有明文 http，账号与会话 cookie 在路上是裸的。

## 二、客户端现在做到的与做不到的

- 做到：扫描手机自身所有私网 `/24`（`Discovery.kt`），首个应答 `GET /api/v1/setup` 的主机胜出，8 秒预算；失败时报告扫了哪些网段、本机地址是什么。
- 做不到：跨网段发现（不可能扫完 172.16/12）、路由器开着客户端隔离时穿透、地址变化后自动跟随。

## 三、候选（Kite 本体侧）

按性价比排序。前三条都不改 API 语义。

| # | 改动 | 手机端能得到的 | 改动面 |
|---|---|---|---|
| 1 | 启动即自述：打印可用地址 + 终端渲染二维码 + 写 `.kite/server.json`；`--addr` 支持 `lan` 之类的简写 | 扫一次码就记住地址，不用查 IP、不用手输 | `internal/cli` 的 run/serve + 一个二维码依赖 |
| 2 | mDNS 宣告 `_kite._tcp.local`（TXT 带版本、站点名、TLS 标志） | 毫秒级发现，不受 `/24` 限制；扫描降级为兜底 | 一个 zeroconf 依赖 + 生命周期；客户端几十行 |
| 3 | `GET /api/v1/setup` 返回服务器自述（版本、站点名、TLS 开关、地址表） | 连上就知道连的是哪台，出错时好诊断 | v1 只增字段，spec 自动跟上 |
| 4 | TLS：`--tls-cert/--tls-key`，或自签 + 控制台指纹，客户端 TOFU 固定 | 远程访问不再是明文；这是公网/隧道方案的前提 | 服务端启动、证书管理、文档 |
| 5 | API Token + Scope（架构文档 §19 的 V3 规划） | 移动端不共享浏览器 cookie 会话，可单独撤销 | 认证、OpenAPI securityScheme |
| 6 | 中继（Kite Cloud 的 rendezvous + relay） | 不在同一网络也能连，且不需要用户自己架隧道 | 独立服务，架构级 |

## 四、与客户端路线图的关系

- 若做 1+2：M5「远程访问/发现」这一节可以大幅缩水——发现交给 mDNS，地址交给二维码。
- 若做 4+5：M5 的 https 与凭据策略才谈得上完整；在此之前，远程只建议走 Tailscale 这类外部加密网络。
- 在此之前，客户端保持现状：扫描 + 手动填地址 + 「测试连接」按钮。

## 五、现阶段替代方案（不改 Kite）

1. **USB 直连**：`kite run`（默认只听回环）+ `adb reverse tcp:1717 tcp:1717`，手机填 `http://127.0.0.1:1717`。最安全，什么都不暴露；拔线即断。
2. **手机开热点、电脑连手机**：手机即网关，与电脑同网段，扫描能命中。
3. **Tailscale**：两端同账号，手机用 `100.x` 地址，任何网络可用，端到端加密。
